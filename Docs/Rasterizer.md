# GaussianSplat — Rasterizer Design

This document covers the rendering pipeline: what it does, the algorithmic choices behind it, and its known open risks. See [`Architecture.md`](./Architecture.md) for the rest of the gem.

## Rendering approach: GPU-projected, GPU-binned, GPU-sorted, GPU-shaded 16x16 tiles

Per-splat screen-space projection, frustum/near-plane culling, and SH color evaluation all run on the GPU, once per splat per frame, in `GaussianSplatProjectCullPass`. Everything downstream of that - grouping surviving splats by screen tile, sorting each tile's splats near-to-far, and final per-pixel shading - also runs on the GPU: a chain of compute passes expands each splat into per-touched-tile entries, radix-sorts those entries by a combined (tile, depth) key, and unpacks the sorted result into the per-tile index/range buffers a tile-shading compute pass consumes. That pass dispatches one 16x16 thread group per screen tile, each group cooperatively loading its assigned splats and compositing them into an offscreen accumulation image, which a second pass then blends into the scene color. This bounds per-pixel work to exactly the splats binning assigned to that pixel's tile, and lets the compute shader terminate early per pixel once accumulated transmittance saturates - see "Known open risks" below for the bounds this design still doesn't enforce.

The pipeline does no CPU-side per-frame work: no CPU frustum test, no CPU binning, no per-frame buffer upload. The feature processor's per-frame job is limited to keeping each pipeline's buffer set correctly sized and the pass chain injected.

## Wave intrinsics are a hard requirement

`GaussianSplatProjectCull.azsl`, `GaussianSplatRadixBuildKeys.azsl`, `GaussianSplatRadixDigitBase.azsl`, `GaussianSplatRadixOnesweep.azsl` and `GaussianSplatRadixUnpack.azsl` all use SM6.0 wave intrinsics (`WaveActiveBallot`, `WaveActiveSum`, `WavePrefixSum`, `WaveActiveAllTrue`, `WaveGetLaneIndex`/`WaveGetLaneCount`, `WaveIsFirstLane`, `WaveReadLaneFirst`, plus `WaveMatchDigit`/`LanesBelowSelf`/`LanesBelowIndex`/`FirstSetLane`/`CountBits4` in [`GaussianSplatWaveOps.azsli`](../Assets/Shaders/GaussianSplats/GaussianSplatWaveOps.azsli)) with **no non-wave fallback path**. The gem therefore requires `RHI::DeviceFeatures::m_waveOperation`, which the Vulkan 1.1 target set in each `.shader` file guarantees here.

This is a deliberate constraint rather than an oversight. The onesweep sort below is built around per-wave ranking and a wave-uniform look-back walk; a scalar fallback would not be a slower version of the same kernel but a different algorithm, and maintaining both is not worth it for a gem targeting desktop-class GPUs. The shaders assume a minimum hardware subgroup size of 32 and handle 32- or 64-wide waves; `MaxWavesPerGroup` is sized from the 32-wide case, and on AMD's 64-wide waves the upper half of those slots simply stays unused.

## GPU-only view culling, plus an explicit per-cloud visibility toggle

All view-based culling is GPU-side and per-splat - there is no CPU frustum test. Each cloud only carries an
explicit show/hide toggle (`SplatCloudData::m_visible`, set via `GaussianSplatFeatureProcessor::SetVisibility`).
Because each cloud gets its own `GaussianSplatProjectCullPass` instance (see below), a hidden cloud is skipped as
a whole pass rather than one early-returning GPU thread at a time: `GaussianSplatProjectCullGroupPass::FrameBeginInternal`
asks `GaussianSplatFeatureProcessor::GetCloudRenderData` whether each cloud contributes anything this frame - it
returns `AZStd::nullopt` for a hidden, empty, or not-yet-resident cloud - and `SetEnabled(false)`s that cloud's pass,
which `AZ::RPI::Pass::FrameBegin` then skips entirely. A cloud that's merely off-screen (still "visible" in the
explicit-toggle sense) still dispatches one GPU thread per splat - each thread rejects itself individually via
`ProjectSplatToScreen`'s `proj.m_valid` (see below) rather than being skipped as a whole cloud - but the per-cloud
pass split is what makes a CPU-side frustum pre-pass a one-line addition here if that ever becomes worth doing.

The rest of the pipeline runs once per frame over every registered cloud. No per-cloud state is uploaded to the GPU
at all: a cloud's transform, multipliers, effective SH degree and visibility are plain `PassSrg` constants its own
cull pass reads straight off the feature processor in `CompileResources`, so there is no descriptor table, no
dirty flag, and nothing that can silently fail to reach the GPU.

- **Project and cull** (`GaussianSplatProjectCullPass`/`GaussianSplatProjectCull.azsl`, **one pass instance per registered cloud**, each dispatching one 64-thread group per 64 splats _of that cloud alone_): `ProjectSplatToScreen` projects each splat into pixel space - position, 2D covariance/conic, a conservative 3-sigma circular radius, and that splat's world-space position - culling splats whose center is behind the camera or nearer than its near plane, splats with a degenerate covariance, and splats fully off-screen. The near plane is recovered from the view's projection matrix by `NearPlaneFromViewToClip` (Atom's `ViewSrg::GetNearZ()` returns depth-linearization coefficients that only coincide with the true near distance under a finite far plane, so it isn't a substitute). Nothing downstream would otherwise reject a splat in front of the near plane - the tile-shading compute shader's only depth test is against the opaque depth buffer, which a splat nearer than everything passes - so it would shade as a smear over every tile its near-degenerate projected covariance touches. A splat that survives culling also has its SH color evaluated once here (`EvaluateShColor`, `GaussianSplatProjectCull.azsl` - it lives there rather than in the shared `GaussianSplatCommon.azsli` header because it addresses this pass's own `PassSrg` and has no other call site) and reserves its own slot in the shared `SplatProjection2D` output buffer spanning every visible cloud.

  That reservation is **wave-aggregated**, not one atomic per splat. Every lane still active at that point owns a surviving splat needing exactly one slot, so a single `WaveActiveBallot` yields both the wave's whole demand and each lane's offset within it; the first active lane performs one `InterlockedAdd` on the shared counter and broadcasts the base via `WaveReadLaneFirst`. This matters specifically because that counter is shared across _every_ cloud's cull pass - it is the single address every thread of every such dispatch contends on. The counter is a fixed-size transient attachment declared in `GaussianSplatVisibleCounterClear.pass`, zeroed at the start of each frame by the RHI's `"LoadAction": "Clear"` on that pass's slot. The slot bound is `m_visibleCapacity` - the capacity of those _shared_ buffers, sized to every registered cloud's splats together, deliberately named apart from this pass's own `m_splatCount` so the two can't be confused; slots past it are dropped rather than corrupting another splat's slot. `GaussianSplatTileShadingPass` then reads the precomputed color straight off each splat's `SplatProjection2D` entry instead of re-evaluating it per tile the splat touches.

Every cloud's static per-splat payload is uploaded to **that cloud's own** pair of GPU buffers - geometry and SH, kept separate for the cache-behavior reasons in `Architecture.md`'s "GPU buffer layout" section - bound into its cull pass's `PassSrg`. `GaussianSplatFeatureProcessor::UpdateCloudSourceBuffers` reads straight out of the loaded `GaussianSplatAsset`'s own `m_data` and `m_shRest` (the feature processor keeps no second host-side copy of the payload, and the cloud's `m_assetData` reference is what keeps those resident until the upload runs) and repacks it per splat into each buffer's own layout: `Packing::PackCloudGeometry` deinterleaves position/rotation/scale/opacity into `SplatGeometry`, `Packing::PackCloudSh` transposes the asset's channel-major SH blocks into the coefficient-major, RGB-interleaved binary16 layout `EvaluateShColor` walks, narrowing the DC term to match. Both uploads are a per-splat CPU pass rather than a byte copy, which is affordable because uploads only happen on asset load or a Max-SH-Degree change, never per frame.

Geometry and SH upload independently, each keyed off the buffer itself rather than a separate dirty flag: geometry repacks when `m_sourceGeometryBuffer` is null, which an asset (re)load forces by clearing it; SH repacks when the asset's degree capped by any `SetMaxShDegree` override differs from `m_uploadedShDegree`, the degree its SH buffer actually holds. `GetCloudRenderData` always reports `m_uploadedShDegree`, never the degree the cloud is headed for, so a cull pass can never evaluate at a degree its own SH buffer wasn't packed for - the one invariant this split depends on. `m_cloudSweepPending` only schedules the sweep on the next `Simulate()`. Adding, removing, or reloading one cloud, or changing one cloud's Max SH Degree, therefore never re-uploads another cloud's payload, which a single concatenated buffer for every cloud could not avoid: any shift in one cloud's base offset would repack them all.

## The sort key

`PackRadixKey` (`GaussianSplatCommon.azsli`) packs `(tileId, quantized depth)` into 64 bits, as two uint32 words: the low word is a monotonic near-to-far quantization of the reverse-Z device depth (`0xFFFFFFFF - round(saturate(depth) * 0xFFFFFFFF)`, so ascending key order is near-to-far), the high word is the tile index. A single combined-key sort therefore produces both the per-tile grouping and the within-tile near-to-far order at once.

The sort covers the key's **low 48 bits only** - `NumRadixRounds` (6) rounds of `RadixDigitBits` (8) each, digit shifts 0/8/16/24/32/40. Shifts 0-24 cover the depth word; 32 and 40 cover the tile word's **low two bytes**. That is the direct reason for the tile-count bound: a tile id above `0xFFFF` has bits that no round ever sorts on, so entries would group wrongly rather than merely imprecisely. `GaussianSplatRadixBuildKeysPass` warns when the tile grid outgrows `MaxSortableTileCount` (`0xFFFF`). At 16x16 tiles that ceiling sits around 16.7 megapixels - e.g. beyond roughly 5460x3070 - so it is real but distant. Raising it costs one more round (`NumRadixRounds` 7, plus the matching `ThreadCountX` literal in `GaussianSplatRadixDigitBase.pass` and the buffer attachment size literals in `GaussianSplatRadixGlobalHistogram.pass`) and therefore one more full pass over the entries.

## GPU tile binning and sorting

Grouping visible splats into per-tile entries and ordering them near-to-far run as a chain of compute passes, all children of the shared parent pass (see "Drawing" below), in the order they appear in `GaussianSplatParent.pass`:

- **`GaussianSplatRadixPrepareBuildKeysDispatchPass`** (`GaussianSplatRadixPrepareBuildKeysDispatch.pass`/`.azsl`): a single-thread pass, run before any splat is expanded into entries. Clamps the GPU-only visible-splat counter to `m_totalSplatCount` (the counter can overshoot, since the cull pass's `InterlockedAdd` runs before its own bounds check) and writes the `DispatchIndirectCommand` that `GaussianSplatRadixBuildKeysPass` launches from, in 256-wide groups - so that pass covers the real visible count rather than the `m_totalSplatCount` upper bound.
- **`GaussianSplatRadixBuildKeysPass`** (`GaussianSplatRadixBuildKeys.pass`/`.azsl`): one thread per visible splat, 256 per group, dispatched indirectly off the args above. Recovers the splat's tile-touch range from its own stored `SplatProjection2D` - `ExtentPixelsFromProjection` inverts the conic to recover the projected covariance's diagonal and reapplies the opacity cutoff, reproducing the extent `ProjectSplatToScreen` culled against, so no per-splat range buffer is carried between the two passes - then expands the splat into one `RadixEntry{ key, visibleSlot }` per touched tile, atomically reserving its own contiguous slice of the fixed-capacity entries buffer out of a **wave-aggregated** `InterlockedAdd` on the entry counter - `WaveActiveSum` gives the wave's whole demand and `WavePrefixSum` each lane's offset within it, so the wave pays one atomic rather than one per splat on the single address every thread of the dispatch contends on, the same aggregation the cull pass applies to the visible counter - a one-uint transient buffer this pass declares and owns in its own template, zeroed by the RHI's `"LoadAction": "Clear"` on the slot rather than by a store in an earlier pass - so the frame's total entry count `E` is bounded only by that capacity, not by a value computed ahead of time. Entries past the capacity are dropped (the inner loop's `writeIndex < m_entryCapacity` guard) rather than corrupting another splat's slice.
- **`GaussianSplatRadixPrepareSortDispatchPass`** (`GaussianSplatRadixPrepareSortDispatch.pass`/`.azsl`): a single-thread pass that reads the entry counter, clamps it to the fixed capacity, and derives the frame's real `blockCount = ceil(E / RadixBlockSize)`. Writes a two-element "Counts" buffer - `[0]` the clamped entry count `E` that every downstream stage bounds-checks against, `[1]` the raw unclamped counter for CPU-side overflow detection - plus two `DispatchIndirectCommand` buffers: one shared by GlobalHistogram/Onesweep, sized in blocks; one for Unpack, sized in 64-wide groups. Those let each stage launch only as many thread groups as `E` actually needs, instead of the fixed capacity. `blockCount` goes only into the indirect args - no GPU stage reads it back as a value.

`RadixBlockSize` is **4096** entries - `NumDigits` (256) threads times `RadixKeysPerThread` (16). It is defined in `GaussianSplatCommon.azsli` and _derived the same way_ by `GaussianSplatFeatureProcessor.cpp`, which sizes the per-block look-back state from it, so the two halves cannot drift apart. More than one key per thread is what makes the onesweep's decoupled look-back pay for itself: all of its bookkeeping - the per-round status-buffer clear, the two status publishes, the look-back chain length - is per block, not per entry, so raising `RadixKeysPerThread` divides all of it by that factor. At one key per thread the look-back cost exceeds the cost of moving the entries themselves. The ceiling is register pressure: each thread holds its entries in registers from the initial read until after the look-back, 3 registers per entry.

### Once per frame, before any round

The sort is an **Onesweep** (Adinets & Merrill), built on the decoupled look-back scan of Merrill & Garland, "Single-pass Parallel Prefix Scan with Decoupled Look-back". Its defining property is that each digit round is a _single_ fused kernel - local histogram, scan and stable scatter over one read of the entries - rather than the separate histogram/scan/scatter passes a textbook LSD radix sort uses. That fusion needs each round's per-digit base offset up front, which three small passes establish once per frame:

- **`GaussianSplatRadixGlobalHistogramPass`**: owns the `[NumRadixRounds][NumDigits]` table as a transient buffer attachment. The table is zeroed by the RHI rather than by a clear shader: the `GlobalHistogramOut` slot declares a `Clear` load action, and because the usage is `Shader` with write access the backend fills the buffer view before the dispatch (`vkCmdFillBuffer` on Vulkan, `ClearUnorderedAccessViewUint` on DX12) with a barrier between the fill and the shader's atomics. The RHI's Metal backend has no buffer-clear path, so the table would not be zeroed there. The pass tallies **every** round's 256-bin histogram in one pass over the entries, one 256-thread group per block, indirectly dispatched. Each block accumulates into an 8 KB groupshared `[round][digit]` tally and folds it into the global table with one atomic per non-empty bin, so per-entry traffic never leaves the group. The shortcut that makes this legal: sorting only _permutes_ the entries, so the multiset of keys - and therefore the count of each digit value at each byte position - is identical no matter how many rounds have already run. Every round's histogram is computable here, from the unsorted input, from one read of each key.
- **`GaussianSplatRadixDigitBasePass`**: one thread group per round (`SV_GroupID.x` selects the round), dispatched directly - its cost and output never depend on this frame's entry count. Turns each round's finished histogram row into that round's per-digit exclusive prefix base, via a wave-level `WavePrefixSum` plus a walk over at most 8 wave totals rather than a log2(256)-step groupshared scan. Every thread group of every round then just reads the result.

### The six digit rounds

Each round is a single **Onesweep** dispatch - one `GaussianSplatRadixOnesweepPass` instance (`GaussianSplatRadixOnesweep0..5` in `GaussianSplatParent.pass`), all six sharing the one `GaussianSplatRadixOnesweepPassTemplate` and authored identically: each derives its round index from the trailing digit of its own name and binds its own buffers from that, so nothing CPU-side has to resolve or push per-round state and the six requests differ only in name.

- **`GaussianSplatRadixOnesweepPass`** (`GaussianSplatRadixOnesweep.azsl`): the whole of one digit round in one kernel, one 256-thread group per block. The look-back state it uses has to start at `StatusNotReady` with the tile counter at 0 for _every_ round; that costs no dispatch, because the `TileStatus` and `TileCounter` slots declare a `Clear` load action and the RHI fills both buffers before each round's dispatch (`vkCmdFillBuffer` on Vulkan, `ClearUnorderedAccessViewUint` on DX12 - the Metal backend has no buffer-clear path). Note this zeroes the status buffer's full capacity rather than only this frame's `blockCount` rows. In order:
  1. **Dynamic tile-id assignment.** `SV_GroupID` cannot be used as the look-back order: GPUs don't guarantee thread groups execute in `SV_GroupID` order, so a group could look back for a predecessor that hasn't launched yet and never make progress. Instead each group fetches a monotonically increasing id from a shared counter, which guarantees whichever physical group runs first gets tile 0 - no predecessor, always completes immediately - and by induction every tile only waits on a group already running or done. That id also selects the block of entries the group owns: fusing the scan into the scatter means a group's chain position and its data must be the same thing.
  2. **Load and rank.** All `RadixKeysPerThread` entries are loaded up front so the loads overlap, and stay in registers for the rest of the kernel - including across the look-back spin - which is what makes this a single read of the entries. The block is split wave-blocked (wave `w` owns a contiguous run) so ranks come out ordered lexicographically by `(waveId, keyStep, lane)`; that order is what makes the ranking _stable_, which correctness across all six rounds depends on. Ranking uses `WaveMatchDigit`/`LanesBelowSelf` and needs no cross-wave synchronisation at all, since each wave accumulates only into its own row of groupshared scratch.
  3. **Block-local scan.** One thread per digit turns that digit's per-wave totals into block-wide exclusive prefixes, yielding this block's own digit totals - the local histogram row a separate pass would otherwise tally and write to memory, here derived for free from the ranking the reorder needs anyway - then a `WavePrefixSum` over those 256 totals gives where each digit's run starts within the block.
  4. **Decoupled look-back.** The group publishes its local count as `StatusAggregate`, then walks backward over predecessor tiles accumulating an exclusive prefix: a `StatusPrefix` predecessor already encodes everything before it and ends the walk, a `StatusAggregate` one only knows its own count so the walk continues, and `StatusNotReady` means spin. Tile 0 skips straight to publishing `StatusPrefix`, which is what bounds every other tile's walk. Status and value publish atomically as a single 32-bit word (status in the top 2 bits, value in the low 30), so a reader can never observe one without the other. The walk is deliberately **wave-uniform** - one `t` for the whole wave - so a step's loads stay one contiguous run instead of degenerating into a gather exactly when contention is highest.
  5. **Staged reorder.** The block is reordered into digit order through a groupshared staging window and only then written out, so the round's scattered traffic stays on-chip and every global write is coalesced. The full block would need `RadixBlockSize * 12` bytes of groupshared - well past the 32 KB limit - so the reorder runs in `StageChunks` passes over a `StageCapacity` (1024) window, keeping the kernel's footprint at ~13 KB so occupancy stays bounded by registers rather than groupshared.

**The rounds ping-pong between two shared entry buffers**, `m_entriesA` and `m_entriesB`, rather than each round owning a private one. `GaussianSplatRadixBuildKeysPass` fills `m_entriesA`, so even rounds read `m_entriesA` and scatter into `m_entriesB` and odd rounds do the reverse. Six rounds is an even count, so the final sorted result lands back in `m_entriesA`, which is what `GaussianSplatRadixUnpack` reads.

That parity, the shared `TileStatus`/`TileCounter` look-back state and the `Counts` buffer are all bound by `GaussianSplatRadixOnesweepPass::BuildInternal` from its round index, rather than wired in `GaussianSplatParent.pass`. `Pass::AttachBufferToSlot` creates an _imported_ attachment keyed on the buffer's own attachment id - the same id a connection would have resolved to - so the frame graph derives identical barriers either way, and the slot's `Clear` load action is unaffected. Only `DigitBase` and `IndirectArgs` stay in the `.pass` file, being transient attachments other passes own.

### After the rounds

- **`GaussianSplatRadixUnpackPass`**: dispatched indirectly, 256 threads per group, one thread per real entry (not the fixed capacity), after the sixth digit round. The entry buffer is globally sorted by `(tileId, depth)`, so every tile's entries form one contiguous run. Unconditionally unpacks each entry's `visibleSlot` into the flat tile-splat-index buffer (the same format `GaussianSplatTileShadingPass` always consumes), then bounds-checks the entry's tile id against the real on-screen tile count before touching the tile ranges, as a defensive guard against an out-of-range key. For an entry at its run's first index it writes that tile's `.m_offset`; every entry in a run contributes to its tile's `.m_count` (order-independent, so no backward/forward boundary scan is needed to derive the run length). Those contributions are **wave-aggregated**: because the entries are globally sorted by tile and lanes hold consecutive entries, a tile's run is a run of adjacent lanes, so the run-start ballot splits the wave into segments and each segment's lowest lane adds its whole segment's length with one atomic. Without that, a wave sitting inside one tile's run would issue 32-64 atomics against the same `.m_count` address and serialize on it.

Near-to-far order is a deliberate choice for the GPU-side compositing approach below (see "Drawing").

## Buffer ownership: the feature processor allocates, the passes attach

Every GPU buffer the chain reads or writes is created and owned by `GaussianSplatFeatureProcessor`, in a single `SplatBuffers` set held **per `AZ::RPI::RenderPipeline`** (`PipelineData::m_buffers`). Passes never allocate; each pass fetches the set for its own pipeline via the free function `GetPipelineBuffers(GetRenderPipeline())` and calls `Pass::AttachBufferToSlot` on its own `Output` slots from inside its `BuildInternal()` override. A pass that finds no set leaves its slots alone rather than half-attaching.

Two separate reasons drive this split, and both are worth keeping in mind before changing it:

**Why the feature processor owns them.** Most of these buffers are read by more than one pass and written by passes that are not their natural "producer" - the entry buffers ping-pong between six rounds, the status/counter buffers are shared by all six, and the projection/touch-range buffers are written by one pass instance per cloud. There is no single producing pass to hang them off. Allocating the whole set in one place also makes the failure mode tractable: `EnsurePipelineBuffers` allocates all of them or none, and the chain is only injected once the set is complete. That matters because a pass that cannot attach a buffer leaves its slot empty, which makes `AZ::RPI::PassValidationResults::IsValid()` reject the pipeline's _entire_ pass tree and `RenderPipeline::UpdatePasses` discard it - taking the rest of the pipeline's rendering down with the splats.

**Why per pipeline.** The contents are per view: two cameras project, sort and shade their own splats, so a shared set would have them overwrite each other.

**Why attaching still happens from `BuildInternal()`.** `AZ::RPI::PassAttachment` never refreshes a `Buffer`-type attachment's size after creation, and `Pass::AttachBufferToSlot` hard-guards against being called twice on the same slot. A buffer therefore has to be attached exactly once, at its final size, from inside the owning pass's own `BuildInternal()` - attaching from outside the pass is also necessarily too late for `PassTree::Validate()`, which only runs on the frame a tree is first `Build()`. This is the same pattern the engine's own `LightCullingPass` and `LuminanceHistogramGeneratorPass` use.

The consequence of all of the above is that **a buffer can never be resized in place** - the chain has to come out, the buffers are rebuilt, and the chain goes back in so every `BuildInternal()` runs again against the new sizes. `Simulate()` drives that: `ArePipelineBuffersStale` compares the current entry capacity, shared splat capacity and tile grid against the sizes the existing set records for itself (`SplatBuffers::m_entryCapacity`/`m_splatCapacity`/`m_tileCountX`/`m_tileCountY`), and on any change calls `RemoveSharedPasses` before `EnsurePipelineBuffers`. The grid rather than the pixel size is compared, so a resize that keeps the tile count leaves the set alone.

Those recorded sizes are also the only sizes a pass bounds its shader by. The live splat total rises in the same `Simulate()` that uploads a newly loaded cloud, and the chain's live frame size moves when a resize reaches its attachments - both a frame or more before the set is rebuilt to match - so a shader bounded by either would index past the end of the buffers it actually has. `GaussianSplatTileShading.azsl`'s dispatch still follows the live frame size, and treats any thread group outside the recorded grid as an empty tile. The buffers and what sizes them:

| Buffer                     | Sized from            | Notes                                               |
| -------------------------- | --------------------- | --------------------------------------------------- |
| `m_entriesA`, `m_entriesB` | entry capacity        | 12 B/entry ping-pong pair; the dominant allocation  |
| `m_tileSplatIndices`       | entry capacity        | flat unpacked splat indices                         |
| `m_tileStatus`             | block capacity x 256  | onesweep look-back state                            |
| `m_tileCounter`            | 1 element             | onesweep dynamic tile-id counter                    |
| `m_splatProjection`        | shared splat capacity | 40 B `SplatProjection2D`                            |
| `m_tileRanges`             | tile count            | 8 B `(offset, count)` per tile                      |
| `m_counts`                 | fixed                 | 2 elements; `m_counts[1]` is the CPU overflow probe |

The tile grid itself is not feature-processor state; `GaussianSplat::TileGrid` (`GaussianSplatTileGrid.h`) derives it from a frame size, with `TileSizePixels` (16) mirroring `GaussianSplatCommon.azsli`'s constant of the same name. The frame size used for allocation is whatever the injected chain has resolved for itself (`TryGetResolvedFrameSize`, read off the parent's own `ColorInputOutput` attachment at the end of `Simulate()`), falling back to the pipeline's root output (`TryGetPipelineFrameSize`) before the chain has ever run, and to 1920x1080 before even that resolves. The root output is only an estimate - a pipeline that rescales between its post-process output and its root makes it larger than the chain's actual size - so the first allocation may be provisional, and the next `Simulate()` simply sees a stale set and rebuilds it around the corrected size. `m_chainFrameSize` deliberately survives a teardown, so the rebuild keeps the corrected value rather than falling back to the estimate that got it wrong.

**Allocation failure is handled rather than fatal.** If any buffer in the set fails to allocate, `EnsurePipelineBuffers` releases the partial set and returns false, and `InjectSharedPasses` leaves the chain out rather than injecting passes whose bindings would fail validation and take the whole pipeline's rendering down. The next `Simulate()` retries, so a transient shortfall - the RHI reclaiming a previous set a few frames late, say - resolves itself; a genuine one leaves the splats hidden while the rest of the pipeline keeps rendering, and the buffer creation logs its own error each attempt. Lower the entry capacity or free GPU memory if it never recovers.

## Drawing

A single `ParentPass` instance (`GaussianSplatParent.pass`, `"PassClass": "ParentPass"`, O3DE's stock generic parent pass - all of this parent's children are declared purely via `PassRequests`/`Connections` in the template) bundles the GPU tile-binning/radix-sort/unpack chain above and the tile-shading + composite passes under one pipeline slot, serving every visible splat cloud in that pipeline.

Its first child is `GaussianSplatProjectCullGroupPass` (`GaussianSplatProjectCullGroup.pass`), a thin `AZ::RPI::ParentPass` subclass that holds the per-cloud projection stage: one template-authored `GaussianSplatVisibleCounterClear` child (always children[0], since `ParentPass::CreateChildPasses` runs `CreatePassesFromTemplate()` before `CreateChildPassesInternal()`) followed by one `GaussianSplatProjectCullPass` per registered cloud, created in `CreateChildPassesInternal` from the feature processor's current cloud set - the same "one child pass per feature-processor-registered object" pattern `SkyAtmosphereParentPass` uses. Each per-cloud child is named `GaussianSplatProjectCull.<handle>`, so every cull pass appends into the one merged buffer set the downstream sort chain consumes. The two shared buffers are owned differently. The **projection buffer** is the feature processor's, because it is sized from the runtime splat count and `AZ::RPI::PassAttachment` computes no size for a `Buffer`-type attachment (`PassAttachment::Update` handles images only); `GaussianSplatProjectCullGroupPass::BuildInternal` attaches it to the group's `SplatProjectionOut` slot _before_ delegating to `AZ::RPI::ParentPass::BuildInternal`, which builds the children that resolve `"Pass": "Parent"` against it. The **visible counter** is a fixed 4 bytes, so it stays data-driven - a `Transient` attachment declared in `GaussianSplatVisibleCounterClear.pass` - and the cull children connect to that sibling directly, since the group's own `VisibleCounterOut` is filled by `SetupOutputsFromTemplate()`, after every child is built. The group re-exposes both as pass-through `Output` slots, so downstream consumers name one pass and one attachment regardless of how many clouds exist. The clear child carries nothing but the counter and the `"LoadAction": "Clear"` that zeroes it - the one thing here needing a scope of its own ahead of every cull dispatch, which a scope-less `AZ::RPI::ParentPass` cannot provide. `GaussianSplatFeatureProcessor::MarkCloudPassesDirty`/`SyncCloudPasses` ask the group to re-create its children when a cloud is acquired or released.

The parent is injected into the render pipeline by `GaussianSplatFeatureProcessor::InjectSharedPasses` (via `AZ::RPI::PassSystemInterface::CreatePassFromRequest`/`RenderPipeline::AddPassAfter`, following the pattern `DiffuseProbeGridFeatureProcessor` uses) from `GaussianSplatFeatureProcessor::AddRenderPasses` - the `FeatureProcessor` virtual `AZ::RPI::Scene::TryApplyRenderPipelineChanges` calls whenever a pipeline is added _or rebuilt_, which (unlike `OnRenderPipelineChanged`'s one-shot `Added` notification) reliably fires even for a FeatureProcessor enabled after the scene's pipeline already exists, since `Scene::AddFeatureProcessor` marks every modifiable pipeline for a rebuild on the next frame. `OnRenderPipelineChanged` is used only for `Removed` cleanup; `InjectSharedPasses` is also called when a cloud is acquired and from every `Simulate()`, in case a pipeline already exists by then or an earlier attempt failed.

`AddRenderPasses` also handles pass hot-reload: `RenderPipeline::UpdatePasses` rebuilds the pipeline's root pass from its descriptor, which the injected chain is no part of, leaving the chain hanging off the discarded root and kept alive only by `m_parentPass`. Detecting that (`m_parentPass->GetRenderPipeline() != pipeline`) and treating the chain as uninjected is what gets it back in. The stale reference is simply dropped rather than routed through `RemoveSharedPasses` - the discarded root is already detached from this pipeline and queued for removal along with everything under it, and queuing the orphan again would make `AZ::RPI::ParentPass`'s removal guard read the state of a pipeline pass tree its parent no longer has, and report the removal as out of phase.

- **`GaussianSplatTileShadingPass`** (`GaussianSplatTileShading.pass`/`.azsl`, a custom `AZ::RPI::ComputePass` subclass): dispatched with `"FullscreenDispatch": true` so one 16x16 thread group covers each screen tile. Each thread loads one splat per batch of 256 into group-shared memory (`s_pixelCenter`/`s_conic`/`s_colorAlpha`/`s_deviceDepth`), then every in-bounds pixel-thread walks the cached batch: a reverse-Z opaque-occlusion test against the pipeline's depth buffer, a per-pixel analytic Gaussian falloff test (evaluating the conic against the pixel offset), and front-to-back "over" compositing with a transmittance accumulator that breaks out of the loop once transmittance drops below `1/255`. The near-to-far tile order from the sort is what makes this early termination correct. A group-shared finished-count lets the whole group stop fetching batches once every one of its pixels is done, rather than each thread idling through the rest of the tile's splats. The pass's only per-pass constant is the shared tile grid size (`m_tileCount`); everything else a pixel needs - conic, opacity, device depth and the **already-evaluated SH color** - comes off the splat's own `SplatProjection2D` entry, since one pass instance serves every cloud and there is no single per-pass model matrix to use. Output goes to a pipeline-owned `R16G16B16A16_FLOAT` accumulation image, sized from the pass's `OpaqueDepth` input and cleared each frame via the slot's `LoadStoreAction`, plus a second `R32_FLOAT` image of the same size holding the per-pixel splat depth (see "Depth output" below).
- **`GaussianSplatComposite.pass`** (`"PassClass": "FullScreenTriangle"`, no custom C++): blends the accumulation image into the scene color with premultiplied-alpha `One`/`AlphaSourceInverse` blending, matching the premultiplied color the tile-shading pass accumulates.
- **`GaussianSplatDepthComposite.pass`** (`"PassClass": "FullScreenTriangle"`, no custom C++, `.azsl` alongside): merges the splat depth image into the pipeline's linear depth buffer. See "Depth output" below.

The parent's `OpaqueDepth`/`ColorInputOutput`/`DepthLinearInputOutput` slots are the only attachments crossing into the surrounding pipeline (wired in `GaussianSplatParentRequest.azasset` to `DepthPrePass.Depth`, `PostProcessPass.Output` and `DepthPrePass.DepthLinear` respectively); the accumulation image handoff between the two children stays entirely internal to the parent, via `"Pass": "Parent"`/child-name `AttachmentRef`s in `GaussianSplatParent.pass`. `GaussianSplatParent.pass` deliberately has no top-level `Connections` entry for `ColorInputOutput` (unlike its pure-`Output`-type `Slots` counterparts elsewhere in the engine, e.g. `SsaoParent.pass`'s `Output`) - `ColorInputOutput` is `InputOutput`-typed, so `Pass::Build()` resolves it in `SetupInputsFromTemplate()`, which runs _before_ `ParentPass::BuildInternal()` creates the children; a `Connections` entry pointing at a not-yet-created child there fails with "Could not find target pass" (compare `DepthParent.pass`'s `PipelineOutput` slot, an `InputOutput` slot with no corresponding `Connections` entry). The composite child's own `"Pass": "Parent"` reference is enough - it aliases directly onto the same attachment the parent's `ColorInputOutput` binding already resolved from the outer `PassRequest`.

**The parent pass is injected immediately after `PostProcessPass`** (`AddPassAfter(parentPass, Name("PostProcessPass"))`), i.e. after the whole post-process parent - and therefore after `TaaPass`, which lives inside it - but before `AuxGeomPass`. Going in after TAA rather than into the forward `"transparent"` draw list is the point: TAA in this pipeline reprojects with `NumJitterPositions: 16` and only 10% current-frame contribution (`Taa.pass`), which needs a correct per-pixel motion vector, and splats never write one. Placing the parent after TAA's accumulation buffer sidesteps that entirely, at the cost of splats not getting TAA's antialiasing/supersampling - acceptable since the per-pixel analytic Gaussian falloff already gives soft, antialiased edges without it.

All visible clouds in a pipeline share one parent-pass instance (one accumulation image, one composite blend) rather than each getting its own: the GPU tile-binning pipeline above merges every visible cloud's splats into one tile-sorted buffer set before the tile-shading pass ever dispatches, so there is exactly one compute dispatch writing the accumulation image per frame - not sequential dispatches per cloud into the same UAV, which would need cross-dispatch hazard tracking this engine's documented behavior doesn't confirm. Because splats from different clouds interleave by device depth within a shared tile's sorted slice, overlapping clouds composite in correct mutual depth order, rather than by pipeline submission order. `RemoveSharedPasses` only needs to `QueueForRemoval()` the parent - `AZ::RPI::ParentPass`'s destructor recursively removes/destroys its children - and runs when the pipeline is removed, when the buffer set goes stale, or when the last cloud is released.

Depth is reverse-Z, and the hardware depth buffer is tested (via the compute shader's manual comparison against `OpaqueDepth`) but never written - splats occlude against (and are occluded by) opaque scene geometry, but never occlude each other via a hardware depth test (only via the near-to-far compositing order within a tile). The pipeline's _linear_ depth buffer is written, by the separate composite pass described next.

## Depth output

Alongside its color, the tile-shading pass writes a per-pixel splat depth, and `GaussianSplatDepthComposite` merges that into the render pipeline's linear depth buffer the same way `GaussianSplatComposite` merges the color into the scene color.

**What "the splat depth of a pixel" means.** Walking a tile's range front to back, a pixel's depth is latched to the reverse-Z NDC depth (`SplatProjection2D::m_deviceDepth`) of the first splat whose compositing pushes that pixel's accumulated coverage `1 - transmittance` to `m_depthCoverageThreshold`. Because the range is sorted strictly near-to-far, that first splat is the nearest one the threshold considers visible, and no later splat can move the latch. The threshold is a single knob spanning the useful range: near `0` it means "the nearest splat that contributes anything at all", while `0.5` gives the median depth, which steps over faint haze in front of a surface. It defaults to `0.02` (`/Robotec/GaussianSplat/DepthCoverageThreshold`) - near-literal, but not settled by a splat contributing under 2% coverage. A pixel no splat settles keeps the image's `0` clear value, which under reverse-Z is also the far plane.

The depth is per _splat_, not per pixel along the ray: every pixel a splat settles gets that splat's center depth, so the map is piecewise-constant over a splat's footprint. This is the usual real-time 3DGS approximation; a per-pixel ray/ellipsoid depth would be a refinement, not a correction.

**The merge.** `GaussianSplatDepthComposite.azsl` converts the latched reverse-Z depth to a view distance with the same expression the engine's own `DepthToLinearDepth.azsl` applies to the depth buffer it is blending into, so both sides of the merge are in the same units, and `discard`s the pixels no splat settled. The merge itself is the render target's `Minimum` blend op (`GaussianSplatDepthComposite.shader`: `One`/`One`/`Minimum`) - per pixel, the nearer of the splat and the opaque surface wins - which is the depth-side analogue of the color pass's premultiplied add, and needs no read-modify-write of the target.

**What this does and does not reach.** The parent pass sits after `PostProcessPass`, so the merged linear depth lands after everything in the stock pipeline that _reads_ `DepthLinear` has already run: the merge is for consumers placed after the splat chain, not for the engine's own post-processing. That is also why the parent re-exposes the buffer as its own `DepthLinearInputOutput` slot - a consumer wanting the merged result addresses it on `GaussianSplatParent`, whereas `DepthPrePass`'s own slot still means opaque-only depth to anything reading it earlier in the frame. In particular, an `AZ::RPI::AttachmentReadback` registered on `DepthPrePass` copies its attachment around _that_ pass's scopes, early in the frame, and therefore sees the pre-merge contents.

The merge is unconditional: the splat depth image is produced, and merged, whenever the splat chain is in the pipeline at all.

## Known open risks

- **Fixed GPU entry-buffer capacity, by design.** The radix-sort entry buffers are sized to a fixed capacity (the `/Robotec/GaussianSplat/RadixEntryCapacity` Settings Registry key, `GaussianSplatFeatureProcessor.cpp`; 16M by default as of this writing - see the main `README.md`'s "Configuration" section), set once in `Activate`, independent of the tile grid or splat/entry counts. `GaussianSplatRadixBuildKeysPass` reserves each splat's slice of this capacity via an atomic counter; `GaussianSplatRadixPrepareSortDispatchPass` reads that counter each frame, clamps it to the fixed capacity, and every downstream stage dispatches indirectly off the resulting real entry count `E` rather than the full fixed capacity. The per-frame GPU cost of those stages is proportional to `E`, not the capacity; the capacity only bounds how large `E` can grow before entries start silently dropping (a scene needing more entries than the configured capacity in a single frame needs the registry value raised) and sizes the buffers those stages read/write. A dense, close-up ~300k-splat cloud needs `E` up to ~2.1M entries in a single frame, measured directly. At the 16M default the two ping-pong buffers alone are ~192 MB each.
- **Overflow is detected only by a sampled readback, not synchronously.** `GaussianSplatRadixPrepareSortDispatchPass` reads the "Counts" buffer's raw unclamped entry count back to the CPU via `AZ::RPI::AttachmentReadback`, at most once every `FramesBetweenCountsReadback` (60) frames and never with a second readback in flight, and raises an `AZ_Warning` when it exceeds the capacity the GPU was given. That is enough to catch a sustained overflow, which is the case that matters - but a one-frame spike between samples goes unreported, and the warning carries no frame identifier: it is logged from the readback callback a few frames after the frame it sampled, and its "this frame" refers to that sampled frame. When splats vanish in dense views and no warning appears, raise the capacity and see whether the symptom moves before ruling overflow out.
- **The near-plane cull tests the splat's center only.** A splat large enough to straddle the near plane pops out whole the moment its center crosses, rather than being clipped to the part still in front of the plane. Clipping a Gaussian against a plane has no closed form (the result isn't a Gaussian), so the alternatives are all approximations - the usual one being to clamp the projection's Jacobian to the near plane and accept a distorted, but continuous, splat. Whether the pop is visible in practice depends on splat sizes relative to the camera's near distance, and hasn't been measured here.
- **A tile's splat count is silently clamped to 65536 at shading time.** `GaussianSplatTileShading.azsl` caps each tile's range length, so a pathologically dense tile drops its farthest splats. Given front-to-back compositing those are the least visible, and transmittance has almost certainly saturated long before - but it is a silent cap with no diagnostic, separate from the entry-capacity drop above.
- **The per-cloud cull passes serialize on the shared visible counter.** Every cloud's `GaussianSplatProjectCullPass` read-modify-writes the same single-element counter and the same shared `SplatProjection2D` output buffer, so Atom's frame graph inserts a UAV barrier between each consecutive pair - N clouds means N sequential dispatches where a single shared cull-pass instance would issue exactly one. Wave aggregation cuts the number of atomics per dispatch by the wave width but does nothing about the barriers between dispatches. For a handful of large clouds the per-cloud split is a clear win (no per-thread cloud lookup, hidden and empty clouds cost nothing at all); for many small clouds the barrier chain can cost more than it saves. The hazard-free alternative - give each cloud its own counter and a reserved region of the shared buffer - would force both `GaussianSplatRadixPrepareBuildKeysDispatchPass` and `GaussianSplatRadixBuildKeysPass` to gather over per-cloud counts instead of reading one atomic, and is not implemented. Measure before assuming either way.
- **The look-back spin assumes forward progress across thread groups.** Onesweep's decoupled look-back requires that a group waiting on a predecessor doesn't starve it. Dynamic tile-id assignment guarantees the chain always terminates at tile 0, so the algorithm is correct on any GPU that eventually schedules every launched group - but it is a spin loop in a shader, and it is the part of this pipeline most sensitive to an unusual driver or a heavily oversubscribed GPU. If the sort ever hangs rather than producing wrong output, this is the first place to look.
- **Projection, binning and sorting are redone in full every frame.** Every visible cloud's splats interleave in one merged, tile-sorted buffer set, and the whole chain runs every frame with no change detection. The tile/depth keys depend on the view, so even a fully static scene re-sorts every frame, and there is no incremental path that re-splices just one changed cloud's contribution into an otherwise-unchanged tile ordering. Per-frame cost scales with the total visible splat count, not with what changed. The per-cloud pass split keeps the _upload_ side free of this - no buffer is re-uploaded per frame, and per-cloud state reaches the GPU only as `PassSrg` constants - but not the sort side.
- **Buffer-size changes rebuild the whole chain.** Because a `Buffer`-type `PassAttachment` can't be resized in place, `Simulate()` tears down and re-injects the entire pass chain whenever `ArePipelineBuffersStale` sees the tile grid or the shared splat capacity move. The tile grid moves when a resize crosses a 16-pixel tile boundary in either axis. The splat capacity is the total splat count of every registered cloud, hidden ones included, so it moves when a cloud with splats is released, when a newly added cloud's asset finishes loading, or when a reload changes a cloud's splat count. Adding, removing, showing or hiding a cloud otherwise only re-creates the per-cloud cull passes (`SyncCloudPasses`). The entry capacity is read once in `Activate`, so it never triggers a rebuild. The rebuild is a visible hitch, not just a cost, and dragging an editor viewport's edge hits it each time the size crosses a tile boundary.
